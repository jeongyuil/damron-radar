# Step 3 구조화 — 장문 전사 청킹 처리 스펙 v1

작성: 2026-07-29 (분석가 초안 · 구현은 엔지니어 재량, 단 §병합 규칙과 출력 스키마는 합의 대상)
배경: 수집 프로토타입에서 "글 내용이 너무 많아 요약 실패" 확인 → 예상된 1차 챌린지.

## 0. 원칙 — 요약이 아니라 추출이다

우리 상품은 영상 요약이 아니다. **긴 전사에서 발언(utterance) 단위 N개를 뽑아내는 것**이다
(PRD §7 "발언이 원자"). 3시간 라이브를 한 번에 LLM에 넣고 "요약해줘"는 실패가 정상:
- 출력 토큰 한계로 뒷부분 발언 유실
- 발언 단위 정밀도(타임스탬프·인용) 붕괴
- 컨텍스트가 커질수록 중간 내용 무시(lost-in-the-middle)

## 1. 파이프라인 위치

```
[2 전사] 자막 or STT (타임스탬프 포함 세그먼트)
              │
              ▼
[3a-0 전처리] 비발화 구간 제거 (광고·음악·무음 — STT 세그먼트 메타 기반)
              │
              ▼
[3a 청킹] 세그먼트를 청크로 병합 (아래 규칙)
              │
              ▼  (청크별 병렬 — Batch API)
[3b 발언 추출] Haiku 4.5 + structured outputs + prompt caching
              │
              ▼
[3c 병합·중복 제거] 결정적 규칙 (LLM 아님, 코드)
              │
              ▼
[3d 적재] utterances INSERT (prompt_version 기록)
```

## 2. 청킹 규칙 (3a)

| 항목 | 값 | 근거 |
|---|---|---|
| 청크 크기 | 전사 텍스트 **~8,000 토큰** (대략 영상 25~35분 분량) | 발언 정밀도 유지 + 출력 여유 |
| 오버랩 | **60초** (앞 청크 끝 60초를 다음 청크 앞에 중복 포함) | 경계에서 잘린 발언 복원 |
| 분할 기준 | 전사 세그먼트 경계에서만 자름 (문장 중간 금지) | STT 세그먼트가 최소 단위 |
| 컨텍스트 | 각 청크에 직전 청크의 **마지막 3~5 발언 요약**을 `[직전 맥락]`으로 첨부(선택, v1.1) | 대명사·화제 연속성 |
| 상한 | 영상 3시간 초과분 절단(`truncated=true`), 3분 미만 쇼츠는 전사 생략 | PRD §4.3 |

토큰 수 계산은 대략치(한국어 ~2자/토큰)로 충분 — 정확한 카운트에 비용 쓰지 말 것.

**전처리(3a-0) 규칙**: LLM 호출 전에 코드로 제거 — ① 무음·음악 구간(STT 세그먼트 공백/
`[음악]` 마커), ② 반복 광고 멘트(동일 채널에서 반복 등장하는 고정 문구 — 등장 빈도 기반 감지),
③ 인트로·아웃트로 정형구. 발화 텍스트는 절대 수정하지 않는다(구간 단위 제거만). 처리량
10~30% 절감 추정. 제거 구간은 로그로 남겨 검수 시 확인 가능하게.

**참고**: 전사가 8K 토큰 이하(대략 1시간 미만 영상)면 청크 1개 = 사실상 단일 호출.
청킹 로직은 그대로 통과하므로 별도 분기 불필요.

## 3. 청크 프롬프트 구성 (3b) — 캐싱 최적화 순서

```
[고정 프리픽스 — prompt caching 대상, 바이트 단위 동결]
  추출 지침 (prompts/structurer/extract_utterances_v1.md)
  이슈 시드 31건 + 엔티티 사전 211건
[가변 — 캐시 뒤]
  영상 메타 (채널·제목·published_at·영상 URL)
  청크 정보: chunk_index, 책임 구간 [own_start_ms, own_end_ms)
  [직전 맥락] (있으면)
  전사 청크 (타임스탬프 포함)
```

- **structured outputs로 `utterances[]` 스키마 강제** — 형식 붕괴·잘림 방지
- 고정 프리픽스는 파일에서 로드해 그대로 사용 — 동적 문자열 삽입 금지(캐시 무효화)
- Batch API로 청크 병렬 제출 (50% 할인, 리드타임 6h 요건과 호환)

## 4. 병합·중복 제거 규칙 (3c) — 결정적, 코드로

**소유권 규칙 (1차, 결정적):**
청크 k는 `[chunk_k_start, chunk_k_end)` 를 **책임 구간**으로 갖는다 (오버랩 60초는 읽기용).
- 발언의 `start_ms`가 자기 책임 구간 안에 있는 것만 채택
- 오버랩 구간에서 추출된 발언(start_ms < own_start_ms)은 **버린다** — 앞 청크가 이미 책임짐
- 프롬프트에도 책임 구간을 명시해 모델이 스스로 거르게 하되, 최종 필터는 코드가 보장

**유사 중복 제거 (2차, 안전망):**
병합 후 start_ms 정렬 → 인접 발언 쌍에 대해
`|start_ms 차| < 10초 AND (quote_excerpt 또는 summary의 자카드 유사도 > 0.7)` 이면 뒤 발언 제거.
(라이브 특성상 같은 말 반복은 실제 발언일 수 있으므로 10초 창을 넘는 중복은 남긴다)

**경계 발언 품질:**
청크 시작 직후 발언이 문장 중간에서 시작하면(오버랩이 못 잡은 케이스) `confidence`를 낮춰
검수 큐에 노출 — 삭제하지 않는다.

## 5. 비용 추정 (D3 예산 내 확인)

가정: 주 100영상, 평균 전사 2만 토큰 → 평균 3청크/영상.
- 입력: 300청크 × (고정 프리픽스 ~6K는 캐시 읽기 0.1×, 가변 ~9K) ≈ 월 12M 토큰 → Haiku 4.5 기준 ~$12
- 출력: 300청크 × ~2.5K ≈ 월 3M 토큰 → ~$15
- **Batch 50% 적용 시 월 ~$14 (약 2만원)** — 상한 15만원의 15% 미만. 물량 2배여도 여유.

## 6. 실패 처리

- 청크 단위 재시도(지수 백오프 3회) → 실패 시 `pipeline_jobs.status='failed'` + 해당 영상
  `processing_status='failed'` — 부분 성공 상태로 적재하지 않는다(지표 왜곡 방지)
- 스키마 검증 실패 응답은 1회 재요청 후 실패 처리

## 부록 A. 검토 — "Gemini에 유튜브 URL 주고 직접 요약" 방식

Gemini API는 유튜브 URL을 입력으로 받아 영상 내용을 직접 이해·요약할 수 있다(Google 공식 기능).
Step 2~3을 한 번에 대체할 수 있어 보이지만, **코어 파이프라인 채택은 비권장**. 근거:

| 관점 | 판정 | 이유 |
|---|---|---|
| 발언 정밀도 | ❌ | 우리 원자 단위는 start_ms/end_ms + **원문 그대로 140자 인용**. Gemini 영상 이해는 근사 타임스탬프·재서술 성향 — "클릭하면 그 발언이 나온다"는 상품 신뢰의 근간이 흔들림 |
| 재현성·검수 | ❌ | 전사(Step 2)와 구조화(Step 3)가 한 덩어리로 불투명해짐 → prompt_version 재현, 골든셋 정확도 측정(§9), 오류 원인 분리(전사 오류 vs 분류 오류)가 불가능 |
| 전사 자산 | ❌ | 검수·재구조화용 전사 전문(90일 보관)이 안 남음. 프롬프트를 갈아끼우고 재처리하려면 영상을 매번 다시 처리해야 함(비용 반복) |
| 물량 한도 | ❌ | Gemini의 유튜브 URL 처리에는 일일 처리량 제한 존재. 31채널 일 30~60시간 영상 상시 처리엔 부적합 |
| 벤더 결합 | ⚠️ | D3(Anthropic 단일)와 충돌, 파이프라인이 Google 정책 변화에 종속 |
| **약관·법률** | ⭕ **유일한 강점** | 유튜브 소유자(Google)의 공식 API 경유라는 점에서, 비공식 자막 추출(경로 A)·오디오 다운로드 후 STT(경로 B)보다 약관 리스크가 낮을 **가능성** |

**결론 및 액션:**
1. 코어 파이프라인은 현행 유지 (자막/STT → 청킹 → Haiku 추출)
2. **법률 자문 Q1에 "경로 C: Gemini 유튜브 URL 공식 처리"를 추가**해 세 경로의 약관 리스크를
   비교 자문받는다 — 만약 경로 A·B의 리스크가 높다고 판정되면, Gemini를 **"타임스탬프 포함
   verbatim 전사기"로만** 쓰는 백업 플랜(Step 2 대체, Step 3는 그대로 Haiku)이 성립한다
3. W3~4에 성환님이 영상 1~2개로 파일럿 비교(전사 정확도·타임스탬프 오차·비용) 해보면 판단 근거 확보

## 부록 B. 청킹 이외 대안 검토 (2026-07-29)

"장문 전사 처리"의 대안 8가지를 비교 검토한 결과. 결론: **고정 청킹 + 결정적 병합이 baseline,
전처리(②)를 보완으로 채택.** 기각 대안은 사유를 남겨 같은 논의의 반복을 방지한다.

| # | 대안 | 판정 | 근거 · 재검토 조건 |
|---|---|---|---|
| ① | 대형 컨텍스트 통짜 처리 (Haiku 200K / Sonnet 1M에 전사 전체 단일 호출) | **부분 채택** | 짧은 영상(≤8K 토큰)은 청크 1개라 이미 단일 호출과 동일. 장편 기각 사유: (a) 출력이 병목 — 3시간 라이브 발언 100~300개 × ~200토큰 = 20K~60K 출력, 잘림 위험 (b) lost-in-the-middle로 중반 발언 유실 (c) 실패 시 전체 재시도 = 비용·리드타임 악화. 재검토: 모델 출력 한계가 크게 늘고 골든셋 리콜이 청킹과 동등해질 때 |
| ② | **전처리·압축** — 광고·음악·무음 제거, 정형구 필터 | **채택 (3a-0)** | STT 세그먼트 메타 기반 코드 필터라 저위험·저비용. 발화 텍스트 무수정 원칙. §2 참조 |
| ③ | 인덱스-then-추출 2단계 — 저비용 1차 스캔으로 "발언 후보 구간"만 마킹 → 후보 구간만 정밀 추출 | **보류 (옵션)** | 잡담·예능 비중 높은 채널(매불쇼 등)에서 처리량 추가 절감 가능. 그러나 1차 스캔이 놓친 발언은 영구 유실(리콜 하락) — 커버리지가 상품 신뢰의 근간이라 실측 없이 도입 불가. 재검토: W5~6 골든셋에서 ②까지 적용한 비용이 예산 초과하거나, 특정 채널 노이즈율이 50%+로 실측될 때 |
| ④ | 의미 단위 청킹 — 임베딩 토픽 경계 감지로 가변 크기 청크 | **v1.1 후보** | 고정 8K 대비 발언 절단·맥락 단절 감소 기대. 단 구현 복잡도↑, 재현성 관리 포인트 추가(경계가 임베딩 모델 버전에 종속). 고정 청킹의 경계 절단률을 W5~6에 실측해 문제가 확인되면 도입 |
| ⑤ | LLM 2-패스 병합 — 청크별 결과를 LLM이 재병합·중복 제거 | **기각 (부분 예외)** | 병합·중복 제거는 결정적 코드 규칙(§4)이 원칙 — LLM 병합은 재현 불가, 검수·정확도 측정(§9) 오염, 비용 2중. 예외: **이슈 매핑 일관성 보정**(같은 영상 내 청크 간 동일 화제가 다른 이슈로 매핑된 경우)만 선택적 경량 2-패스 후보로 남김 — 이 역시 룰 기반(동일 키워드 → 다수결)을 먼저 시도 |
| ⑥ | 유튜브 챕터·타임스탬프 구조 활용 분할 | **기각** | 정치·시사 라이브에 챕터가 거의 없음 — 커버리지 확보 불가. 있으면 참고 메타로만 |
| ⑦ | 출력 축소 — 필드 최소화 추출 후 필요 발언만 2차 상세화 | **기각** | utterances 스키마(§7)가 상품 최소 단위 — 필드를 깎으면 지표·리포트가 성립 안 함. 2차 상세화는 왕복 2배로 이득 없음 |
| ⑧ | Gemini 유튜브 URL 직접 처리 | 부록 A 참조 | 코어 비권장. 법률 자문 Q1 '경로 C' + Step 2 대체 백업 플랜으로만 유지 |

### 종합

- **지금 구현할 것**: 3a-0 전처리 + 고정 청킹(8K·오버랩 60초) + 결정적 병합 — 이 조합이
  리콜(커버리지)·재현성·비용의 균형점
- **실측 후 판단할 것**: ③(노이즈 채널 옵션), ④(의미 단위 청킹) — W5~6 골든셋·500건 육안
  점검에서 경계 절단률·노이즈율 데이터가 나오면 결정
- **원칙 재확인**: 발언 커버리지(리콜)가 최우선 — 비용 최적화가 리콜을 깎는 방향의 대안은
  실측 근거 없이 도입하지 않는다

## 부록 C. 검토 — "RAG 방식 요약" (전사를 RAG DB에 저장 후 요약, Snowflake Cortex Search)

엔지니어 제안(2026-07-29) 검토. 결론: **RAG는 Step 3(추출)의 대안이 아니라 Step 4~5(검색·
리포트)의 구성요소다.** 방향은 맞고 단계가 다르다 — 그리고 그 자리는 이미 스키마에 설계돼 있다.

### 1. RAG가 푸는 문제 vs 우리 Step 3 문제

| | RAG (검색 증강) | 우리 Step 3 (구조화) |
|---|---|---|
| 목적 | 질의에 **관련된** 것을 찾아 답변 | 전사의 발언을 **빠짐없이** 추출 |
| 커버리지 | top-k 검색 = 의도적 표본 추출 | 전수 처리 (리콜 최우선 원칙) |
| 실패 모드 | 검색 안 된 내용은 **조용히 누락** | 청크 실패 시 명시적 failed 처리 |

"RAG DB에 넣고 요약"의 실제 동작: 전사를 청킹→임베딩→질의로 top-k 청크 검색→그것만 요약.
즉 ① **어차피 청킹은 해야 하고**(RAG의 전제), ② 검색에 안 걸린 발언은 지표 분모에서 영원히
사라진다. 예: 뉴스공장 3시간에서 사법개혁 발언 특징이 임베딩 질의와 어긋나면 그 발언은 누락
— 어떤 발언이 빠졌는지조차 알 수 없다. **발언 유형 정확도 85%·커버리지 95%(§1 게이트)를
RAG 표본 추출로는 보장할 수 없다.**

### 2. 저작권 설계와의 충돌 (단, 원칙 자체는 자문 검증 대상)

**전제 명확화**: §7.3 "전사 90일 파기·파생 데이터만 자산화"는 법 조문이 아니라 우리가 리스크를
낮추려 세운 **자체 설계 원칙**이며, W3~4 법률 자문 Q1이 정확히 이 설계의 유효성(+90일 적정성)을
검증하는 안건이다. 자문 결과 "전문 보존도 저리스크"로 나오면 RAG-over-전사도 재검토 가능.

**개발 단계 운영 결정(2026-07-29)**: 자문 전까지 개발 단계에서는 전사 보관·실험을 **열어두고**
진행한다. 가드레일: ① 외부 제공·판매 금지(D6 기본안 유지) ② 전사는 자산 DB와 분리 보관해
자문 결과에 따라 **일괄 파기 가능한 구조**로 ③ 보존 기간·파기 정책은 자문 후 D6에서 확정.

전사 전문을 RAG DB에 **영구 자산화·외부 제공**하는 것은 현행 설계와 충돌한다(위 전제 참조).
발언 단위 임베딩은 무관 — 요약·140자 인용만 담으므로 원칙 안에 있음. 90일(개발 단계에서는
잠정 무기한) 내부 보관 중 전사에 검색 인덱스를 붙여 처리·검수에 쓰는 것은 목적 내 사용으로 허용.

### 3. 성환님 직감이 맞는 지점 — RAG의 올바른 자리

**RAG는 "추출된 발언 DB" 위에서 동작한다.** 이미 설계에 들어 있음:
- `utterances.embedding VECTOR(1024)` (schema/001_init.sql) — 발언 단위 임베딩
- 유사 발언 검색·이슈 클러스터링 (PRD §2 Step 3, §6.4)
- **상품 기능이 곧 RAG**: "발언 검색 아카이브"(대시보드 구독 상품), 리포트 코멘터리 작성 시
  이슈별 관련 발언 검색, 팩트체크 단서 큐(지표 ⑥)의 유사 주장 묶기
- 흐름: `전사(한시) → [전수 추출] → utterances(영구, 임베딩 포함) → [RAG 검색/집계] → 상품`

### 4. Snowflake Cortex Search 평가

훌륭한 제품이지만 **Phase 1 우리 조건에서는 과함**:

| 기준 | 판단 |
|---|---|
| 규모 | 발언 연 수십만 건 수준 — pgvector가 여유 있게 커버(수백만 건까지 무리 없음) |
| 비용 | Cortex Search는 상시 서빙 컴퓨트+크레딧 과금 — 인프라 예산(VPS 월 3~8만원) 대비 별도 플랫폼 상시 비용. PRD 비용 원칙("3개월 뒤 버려도 아깝지 않은 도구") 위배 소지 |
| 스택 | §2 기본안이 "PG+pgvector 한 곳에서"인 이유 = 관계형 지표 집계와 벡터 검색이 같은 DB. Snowflake 추가 시 동기화 파이프라인·이중 운영 발생 |
| 강점 발휘 조건 | 이미 Snowflake에 데이터가 있거나, 하이브리드 검색을 대규모 트래픽에 서빙할 때 — 둘 다 Phase 1 아님 |

**전환 트리거(재검토 조건)를 명시해 두자**: ① 발언 수백만 건+에서 pgvector 검색 품질/속도
한계 실측 ② Phase 3 셀프서브 대시보드의 검색 트래픽 본격화 ③ 하이브리드(키워드+벡터) 검색
요구가 상품 요건이 될 때. 그 전까지는 pgvector(+필요시 PG FTS로 하이브리드 흉내)로 충분.

### 5. 결론

1. Step 3는 부록 B 결론 유지: 전처리 + 청킹 + 전수 추출 (RAG로 대체 불가 — 리콜·법률)
2. RAG는 **utterances 위의 검색 레이어**로 Phase 1에 이미 포함(pgvector) — 성환님이 이
   레이어(임베딩 생성·유사 발언 검색 쿼리)를 소유하고 설계하면 정확히 그 직감이 실현됨
